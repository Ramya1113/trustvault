# TrustVault Security Threat Model & Mitigations

This document outlines the primary security threats addressed by TrustVault, the server-side architectural mitigations implemented in the codebase, and the automated tests proving their effectiveness.

Only threats with active mitigations in the current codebase are listed below.

## Audit-Chain Limits & Operational Boundaries

The cryptographic audit chain provides strong tamper-evidence, but administrators and operators should be aware of its specific operational boundaries and guarantees:

1. **In-Process Thread Lock Scope:**
   - The current per-tenant lock (`_get_org_lock(org_id)`) uses Python's `threading.Lock`. This guarantees strict serial consistency across concurrent threads within a single Python runtime (such as multi-threaded Gunicorn or development servers).
   - In a multi-worker process deployment (e.g., Gunicorn with multiple worker processes `-w 4`) or a multi-instance container cluster, in-memory locks do not span separate OS processes. To maintain strict serial hash chaining across independent OS processes or containers, database-level locking (`SELECT ... FOR UPDATE` or advisory locks in PostgreSQL) or an isolated asynchronous audit queue/sequencer worker is required.

2. **Detection vs. Prevention of Raw SQL Mutation:**
   - The audit log is tamper-evident, not write-proof at the physical storage layer.
   - SQLAlchemy ORM listeners block `session.delete()` and `session.update()` at the application tier.
   - However, an attacker with direct root database credentials (`psql` or direct disk access) can alter rows outside the application. If this occurs, the chain cannot prevent the edit, but `verify_chain(org_id)` will mathematically detect the tampering and identify the exact broken row index.

3. **Chain Truncation and Complete History Regeneration:**
   - If a privileged database administrator modifies an audit entry and subsequently recalculates and updates the hashes of all subsequent rows in that tenant's chain, the local chain will appear mathematically valid in isolation.
   - To mitigate full-chain rewrite attacks, production architectures require periodic external checkpointing (e.g., anchoring the latest `entry_hash` to a write-once cloud storage bucket, digital timestamping service, or public ledger).

4. **Tenant Isolation of Non-Existent User Probes:**
   - `AuditLog` enforces a non-nullable foreign key `org_id` to maintain multi-tenant cryptographic isolation.
   - Failed authentication attempts for unknown usernames cannot be chained into a tenant's audit trail without arbitrarily polluting a tenant's log or leaking information. They are captured via application security logs (`current_app.logger.warning`) with the source IP address and username.
